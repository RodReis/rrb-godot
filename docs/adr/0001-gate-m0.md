# ADR-0001 — Gate do M0: Godot 4 + netfox para ação em rede

**Status:** aceito — 2026-10-09
**Data do teste:** 2026-10-09
**Decisor:** Rodrigo Reis (PI)
**Relacionados:** PRD §9.1 e §10.3 (risco R1), `docs/prd/mvp/MVP-0.md`, issue #7, roteiros `game/test/net/roteiro-f3..f5-*.md`

## Contexto

O PRD exige provar, antes de qualquer conteúdo, que Godot 4.7 + netfox entrega movimento com predição e um ataque validado no servidor **jogáveis a 100 ms de RTT**. Se não entregar, o projeto migra para Unity (Fish-Net ou Photon Fusion) antes do M1.

O spike (F1–F5, PRs #8–#14) entregou:
- servidor headless autoritativo em Docker com `tc netem`;
- 2 clientes com movimento por rollback (`RollbackSynchronizer`, input só por `BaseNetInput`, input do cliente validado no servidor);
- ataque corpo a corpo resolvido só no servidor, com o dano aplicado pelo `HitLedger` no `_rollback_tick` do alvo;
- HUD de RTT/tick e autopilot para teste solo.

Desvios do plano e riscos conhecidos estão nos comentários de encerramento dos cards #2–#6.

## Protocolo

O Code sobe o servidor em Docker e os 2 clientes (o 2º em autopilot). O PI controla o cliente 1. Cada cenário dura ~10 minutos (tick final ≥ 20 000 a 30 Hz).

| Cenário | Ambiente |
|---|---|
| A — base | sem `NETEM_*` |
| B — alvo do gate | `NETEM_DELAY_MS=100`, `NETEM_LOSS_PCT=2` |
| C — estresse | `NETEM_DELAY_MS=200`, `NETEM_JITTER_MS=30`, `NETEM_LOSS_PCT=5` |

`NETEM_DELAY_MS` é o **RTT total**, dividido metade na saída e metade na entrada do container (IFB). A perda vale nas duas direções. Ver "Ajuste do ambiente de teste".

## Checklist

| # | Critério | A | B | C |
|---|---|---|---|---|
| 1 | Movimento próprio responde sem atraso perceptível | OK | OK | OK |
| 2 | Player remoto se move suave, sem teleporte | OK | OK* | **Falhou** — remoto trava, difícil de encostar |
| 3 | Sem "borracha" (correção visível da própria posição) ao andar contra obstáculos | OK | OK | OK |
| 4 | Acerto em alcance reduz 92 HP nas duas janelas | OK | OK | OK |

| 6 | HP idêntico nas duas janelas após 10 min | OK | OK | OK |

\* B falhou no item 2 na primeira rodada, com `netem` assimétrico (100 ms só na saída do servidor). Passou após o ajuste do ambiente de teste, dentro da janela de ajuste prevista pela regra de decisão.

**Regra de decisão:**
- **Segue Godot** se B tiver todos os itens OK.
- **Migra para Unity** (Fish-Net ou Photon Fusion) antes do M1 se, no cenário B, os itens 1, 2, 3 ou 6 falharem e não se resolverem em até 2 dias de ajuste (tickrate, interpolação, configuração do netfox).
- C é informativo e não bloqueia.

## Ajuste do ambiente de teste

Na primeira rodada do B, o player remoto travou cada vez mais (relato do PI: "muito lag"). Medição com instrumentação temporária no cliente 1, olhando o autopilot (frames parados de cada 120, a 60 fps):

| Condição (35 s cada, salvo indicado) | Frames parados | Maior salto | Atraso do estado |
|---|---|---|---|
| A, sem latência | 0–2 | 0,13 u | 0,6 tick |
| 100 ms só na saída, sem perda | 0 → 22, crescendo | 0,43 u | 4,0 → 4,1 ticks |
| Só 2% de perda, sem atraso | 4–12, estável | 0,22 u | 0,5 tick |
| B original (100 ms numa direção, 2%) | 14 → 90, crescendo | 1,47 u | 4,1 → 4,8 ticks |
| 50 + 50 ms, 2% por direção | 2–20, estável | 0,42 u | 4,0–4,1 ticks |

- Throttle do ENet no servidor: 32/32 o tempo todo, então não é a causa.
- **Causa:** atraso só numa direção desalinha o relógio do netfox, que supõe ida e volta simétricas. Os estados do remoto passam a chegar em rajadas cada vez mais desalinhadas.
- **Ajuste (decisão do PI):** `infra/gameserver/entrypoint.sh` divide o RTT entre saída (`eth0`) e entrada (`ifb0`). Na internet real o atraso é aproximadamente simétrico, então o RTT medido segue em ~115 ms.

## Medições (rodadas oficiais)

| Cenário | RTT no HUD | `ERROR`/`WRN` servidor | `ERROR`/`WRN` clientes | Remoto parado (média) | Atraso do estado |
|---|---|---|---|---|---|
| A | 18–21 ms | 0 / 0 | 0 / 0 | 2,2% | 0,6 tick |
| B (simétrico) | 113–124 ms | 0 / 0 | 0 / 0 | 19,6% | 3,8 ticks |
| C | 212–215 ms | 0 / 0 | 0 / 696 e 372 | 79,1% | 8,5 ticks |

No C, os avisos dos clientes são todos `netfox::DiffHistoryEncoder: Reference tick N missing`. Com 5% de perda e jitter, os estados enviados como diferença chegam sem o estado de referência e são descartados, e o remoto congela.

## Decisão

**Segue Godot 4.7 + netfox.** O cenário B (100 ms de RTT, 2% de perda) passou nos 7 critérios: movimento próprio imediato, remoto suave, sem borracha, dano idêntico nos dois clientes, 0 erros no servidor. O MVP1 está liberado.

## Alternativas descartadas

| Alternativa | Por que não |
|---|---|
| Migrar para Unity (Fish-Net ou Photon Fusion) | O gate passou no cenário alvo. Migrar custaria refazer F1–F5 sem ganho comprovado. |
| Manter o `netem` assimétrico e compensar no jogo (`display_offset`/`input_delay` do netfox) | Atrasaria também o movimento próprio (item 1) para corrigir um artefato do ambiente de teste que não existe na internet real. |
| Decidir com o B reprovado na primeira rodada | A regra prevê até 2 dias de ajuste. A causa foi medida e corrigida no mesmo dia. |

## Consequências

- **Positivas:** a base de rede (rollback, servidor autoritativo, dano no servidor com `HitLedger`, input validado) segue para o MVP1. O ambiente de teste com `netem` simétrico vira o padrão.
- **Custos:** nenhum retrabalho. O `entrypoint.sh` mudou a semântica de `NETEM_DELAY_MS` (agora RTT total).
- **O que vigiar:**
  - Suavidade do remoto sob perda alta (C: 79% de frames parados). Candidatos de ajuste no netfox: `full_state_interval` menor, `diff_ack_interval` > 0 ou desligar diff states (`netfox/rollback/enable_diff_states`). Reavaliar quando houver mais entidades em rede (F20, MVP2).
  - Mesmo no B, ~20% dos frames têm o remoto parado, imperceptível para o PI. Revalidar com teste entre duas máquinas reais (MVP3).
  - Rollback preso no tick do sync quando o cliente trava ~1,4 s com shaders frios (visto uma vez no F3).
